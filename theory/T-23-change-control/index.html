    T-23 整合變更控制 (Integrated Change Control)¶

    變更控制是一條讓「改變」被看見、被評估、被決定、被記錄的路；它不是為了阻擋變更，而是確保每一次改變都是有人知情並同意的取捨。

     提出變更請求 (W-16)
     │
     ▼
 PM 評估影響：範疇 / 時程 / 成本 / 品質 / 風險
     │
     ▼
 有權者決定 ─┬─ 核准 ──► 更新基準與計畫 ──► 通知相關人
 (CCB 或     ├─ 退回 ──► 記錄理由 ──► 通知提出者
  發起人)    └─ 延後 ──► 放入待議清單
     │
     ▼
 變更紀錄表：每一筆都留下來

    白話解釋

    • 變更請求 (Change Request)：任何要修改已核准基準（範疇、時程、成本）的提議。
    • 變更控制委員會 (Change Control Board, CCB)：有權核准變更的人或群體。小專案可能就是發起人一個人。
    • 整合：一個變更通常會同時影響多個面向，加一個功能會影響時程、成本、測試、風險。所以評估時要一起看，不能只看一個面向。

    分級處理很重要：

    等級 範例 誰核准
    小 在浮時內、不影響預算 PM
    中 影響里程碑但不影響最終交付日 發起人
    大 影響最終交付日、預算或主要範疇 CCB / 治理單位

    IT 例子

    注意：專案管理中的「變更控制」和 IT 維運中的「變更管理」（例如 ITIL 的 Change Management，管理對生產環境的修改）是兩件不同的事。前者管的是專案計畫的變更，後者管的是系統的變更。網路割接通常兩者都要走。

    最常見的誤解

    「變更流程 = 官僚。」流程太重的確會變成官僚，但沒有流程的後果是「範疇悄悄變大、時程卻沒動」，最後由團隊加班買單，見 T-10 範疇蔓延。

    取捨與兩難

    • 流程的重量要和變更的影響成比例。所有變更都要開 CCB，大家會想辦法繞過流程；完全沒有分級，小事也會拖很久。
    • 【敏捷】 中，待辦清單本身就是變更機制：新需求進清單，由產品負責人排序。但對外部合約、預算上限的變更，仍需要正式流程。
    • 什麼時候不適用嚴格變更控制：探索、研究、原型階段，此時變更就是學習的方式。

    跨主題的互動

    • 要拒絕或延後變更時，怎麼說得不傷關係，見 P-06 說不與期望管理。
    • 變更的決策權屬於治理架構的一部分，見 T-24 治理與階段關卡。

    資深 PM 怎麼判斷

    資深 PM 的習慣是：沒有評估過的變更，不給答案。被問「這個加進去可以嗎？」時，回答「我評估一下影響，明天給你選項」，而不是當場說好或不好。

    明天上班可以怎麼用¶

    • 和發起人約好變更的分級標準：哪些你可以自己決定、哪些要他決定。
    • 建立變更紀錄表，即使是已經口頭答應的變更也補記，模板見 W-16 變更請求單。
    • 每次核准變更後，記得更新時程表和預算，並通知受影響的人。

    對照案例¶

    • C-01 Denver 機場行李系統：建造期間的設計變更，在開幕日固定的情況下層層累積。
    • C-03 FBI Virtual Case File：開發期間大量的需求變更。

    小測驗¶

    一位處長在電梯裡跟你的工程師說：「割接的時候順便把 B 棟的設備也一起換掉吧。」工程師回來跟你說處長已經同意了。你應該？

    • A. 照做，處長已經同意了
    • B. 拒絕，因為沒有走流程
    • C. 請處長或其代表提出正式的變更請求，你評估對時程、成本、割接風險的影響後，提交給有權者決定
    • D. 讓工程師自己決定要不要做
    看答案與解析

    答案是 C。

    • A 錯： 口頭的「同意」不是評估過的決定。B 棟設備可能需要額外的採購、停機窗口和測試，處長在電梯裡不可能知道這些影響。
    • B 錯： 直接拒絕高層會傷害關係，也可能錯過真正合理的需求。
    • C 對： 把非正式的要求導入正式流程，讓決定基於資訊，也保護工程師不必獨自承擔後果，見 W-16 變更請求單。
    • D 錯： 讓工程師決定範疇變更，超出了他的權責，見 T-19 責任分派與 RACI。
