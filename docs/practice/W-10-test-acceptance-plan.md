# W-10 測試與驗收計畫 (Test & Acceptance Plan)

**事先寫好要測什麼、怎麼測、通過標準是什麼、誰來簽核，讓「上線準備好了沒」可以用證據回答。**

```text
 測試的層次（由小到大）

 單元測試   單一設備、單一設定是否正確
     │
     ▼
 整合測試   設備之間、系統之間是否正常互通
     │
     ▼
 效能測試   在預期負載下是否達標
     │
     ▼
 故障測試   元件故障時是否如預期切換
     │
     ▼
 使用者驗收  使用者實際操作，確認符合需求
 UAT
     │
     ▼
 簽核 ──► 上線
```

=== "入門"

    **測試計畫的內容**

    1. **範圍**：測什麼、不測什麼。
    2. **環境**：在哪裡測（測試環境、生產環境的維護窗口）。
    3. **測試案例**：每一條對應到需求，見 [W-03 需求追溯矩陣](W-03-requirements-traceability.md)。
    4. **通過標準**：每個案例的預期結果。
    5. **時程與人員**。
    6. **缺陷處理**：發現問題時的分級與處理方式。
    7. **簽核**：誰簽、依據什麼簽。

    **測試案例範本**

    | 編號 | 對應需求 | 測試步驟 | 預期結果 | 實際結果 | 通過 |
    |---|---|---|---|---|---|
    | TC-05 | R-01 | 在持續流量下拔除主線 | 1 秒內切換、連線不中斷 | 切換 0.4 秒 | 是 |
    | TC-09 | R-02 | 以無 MFA 帳號登入管理介面 | 登入被拒 | 登入被拒 | 是 |

    **缺陷分級範例**

    | 等級 | 定義 | 上線前要求 |
    |---|---|---|
    | P1 | 影響核心功能或資安 | 必須修正 |
    | P2 | 影響部分功能，有替代方式 | 需發起人同意才能帶著上線 |
    | P3 | 輕微、外觀 | 可列入後續改善 |

    **最常見的錯誤**

    測試計畫在專案後期才寫。到那時測試時間往往已經被壓縮，也來不及準備測試環境。

=== "進階"

    **故障測試特別重要**

    網路和基礎架構的價值常在「出事的時候」：備援能不能切、告警會不會響、回退能不能做。這些只能靠刻意製造故障來驗證，而且需要提早申請窗口。

    **驗收的權責**

    使用者驗收 (UAT) 應由接收方主導，專案團隊提供支援。如果專案團隊自己測、自己簽，驗收就失去意義。

    **資深 PM 的檢查問題**

    - 每一條「必要」需求，是否都有測試案例？
    - 驗收簽核人在測試計畫階段就同意了通過標準嗎？

## 小測驗

上線前一天，測試發現一個 P2 缺陷（報表匯出偶爾失敗，但可以重試成功）。依照上面的分級規則，正確的處理是？

- A. 一定要修好才能上線
- B. 不用管，P2 不重要
- C. 向發起人說明缺陷、影響、替代方式與預計修正時間，由他決定是否帶著上線
- D. 由測試人員自行決定

??? success "看答案與解析"
    **答案是 C。**

    - **A 錯：** 依分級規則，必須修正的是 P1。
    - **B 錯：** P2 不是可以忽略，而是需要被看見並被核准。
    - **C 對：** 依事先約定的規則，讓有權者在充分資訊下決定，並記錄這個決定。
    - **D 錯：** 測試人員負責發現與記錄，不負責決定上線。
