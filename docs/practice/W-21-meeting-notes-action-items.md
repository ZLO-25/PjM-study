# W-21 會議紀錄與行動項目追蹤 (Meeting Notes & Action Items)

**會議紀錄的目的不是記下「誰說了什麼」，而是留下三樣東西：做了哪些決定、誰在什麼時候之前要做什麼、還有哪些事沒定案。行動項目追蹤則是確保這些承諾在下一次開會前真的被做掉。**

```text
 一場會議的三種產出

 ┌─ 決定 Decisions
 │    「選方案 B」「上線日改為 5/20」
 │    → 寫進決策紀錄，之後不再重新討論
 ├─ 行動項目 Action Items
 │    一個人 + 一件事 + 一個日期
 │    → 進追蹤表，每天掃一次到期的
 └─ 待定 Open Questions
      「資安審查要幾天？」
      → 指定誰去問、何時回來

 沒有這三樣東西的會議，等於沒開。
```

=== "入門"

    **會議紀錄範本（一頁以內）**

    ```text
    會議：核心網路割接 週會 #7
    時間：2026-xx-xx 14:00–14:30
    出席：（角色即可，不必全名）

    決定
    D-12 割接窗口定為 5/18 (六) 22:00–02:00
    D-13 回退決策點定為 00:00，由網路主管擔任指揮官

    行動項目
    A-31 完成實驗室演練並記錄各步驟時間   網路組長   5/10
    A-32 寄出使用者停機公告              溝通窗口   5/12
    A-33 確認原廠當晚支援窗口            PM         5/9

    待定
    Q-05 資安是否需要在割接後重新掃描？  由 PM 問資安  5/9

    上次行動項目：A-28 完成、A-29 完成
                A-30 延到 5/10（設備晚到）
    ```

    **行動項目的三個必要欄位**

    1. **一個人**：不是「網路組」，是一個名字。兩個人負責等於沒人負責。
    2. **一件可以驗證完成的事**：「研究一下」不是行動項目；「提出兩個方案並附估算」才是。
    3. **一個日期**：不是「盡快」。

    **追蹤表怎麼做**

    用一張表就好，可以是試算表、工單系統或 RAID 日誌裡的一個分頁。欄位：編號、內容、負責人、到期日、狀態、來源會議。每天花 10 分鐘掃一次「今天到期」與「已逾期」。

    **什麼時候寄出**

    會後 24 小時內，最好當天。超過一天，大家對「我們決定了什麼」的記憶就開始分歧。

    **IT 例子**

    割接前的協調會上，大家口頭同意「應用團隊會在割接前改好 IP」。沒人記下來是誰、哪一天。割接當晚才發現有三台伺服器沒改。這不是應用團隊的錯，是這個承諾從來沒變成一條有人名與日期的行動項目。

    **最常見的誤解**

    「會議紀錄要寫得很詳細才專業。」錯。沒人會讀三頁的逐字稿。一頁之內、決定與行動項目放最上面、30 秒看得完的紀錄，才會被讀、被執行。

=== "進階"

    **決策紀錄為什麼要單獨保存**

    把所有「決定」從各次會議紀錄中抽出來，另外維護一份依時間排序的決策紀錄 (Decision Log)。三個用途：

    - 新加入的人可以在一小時內知道專案為什麼長成現在這樣。
    - 有人想重開已經決定的事時，你可以說「這在 3/12 的會議決定過了，當時的理由是 X；如果條件變了，我們走變更流程」，見 [T-23 整合變更控制](../theory/T-23-change-control.md)。
    - 復盤時可以回頭看：哪些決定是在資訊不足時做的，見 [T-29 經驗回顧與復盤](../theory/T-29-lessons-learned.md)。

    **行動項目一直逾期怎麼辦**

    逾期本身是資訊。連續逾期通常不是「那個人懶」，而是：

    - 他沒有真正同意，只是會議上不好說不，見 [P-14 團體迷思](../psychology/P-14-groupthink.md)、[P-11 心理安全感](../psychology/P-11-psychological-safety.md)。
    - 他的職能經理給他的優先順序不一樣，見 [T-20 矩陣式組織](../theory/T-20-matrix-organization.md)。
    - 這件事其實比大家想的大，應該拆成一個工作包而不是一條行動項目。

    資深 PM 遇到逾期，第一個動作是私下問「這件事卡在哪？」而不是在會議上點名。

    **【敏捷】團隊的版本**

    Scrum 團隊的每日站會不留會議紀錄，行動項目就是看板上的卡片；但 Sprint 回顧的改善項目仍然需要「一個人、一件事、一個日期」，否則回顧會變成每次都在抱怨同樣的事，見 [T-25 敏捷價值與 Scrum](../theory/T-25-agile-scrum.md)、[W-18 主持復盤會議](W-18-retrospective.md)。

    **資深 PM 怎麼判斷一場會該不該開**

    問一句：「這場會結束時，要做出什麼決定？」如果答案是「同步資訊」，改成一封信或一份報告。如果答案是「要決定 X」，確認能決定 X 的人會出席；他不在，就改期。

## 明天上班可以怎麼用

- 把你下一場會議的紀錄改成「決定 / 行動項目 / 待定」三段，一頁以內，會後當天寄出。
- 開一張行動項目追蹤表，把過去一個月所有會議中的口頭承諾補進去。你會發現至少三件事其實沒有負責人。
- 在每場會議的最後 3 分鐘，把行動項目唸一遍，請每個負責人當場確認日期。
- 建一份決策紀錄，從今天開始記。

## 對照案例

- [C-08【模擬】核心網路割接](../cases/C-08-sim-network-cutover.md)：「00:00 回退」這個決定因為被明確記錄、有指定的人執行，才在壓力下發揮作用。
- [C-10【模擬】跨廠區建置](../cases/C-10-sim-multi-site-buildout.md)：跨廠區團隊各做各的，常常源於會議決定沒有被寫下來並傳到每個廠區。
- [C-03 FBI Virtual Case File](../cases/C-03-fbi-virtual-case-file.md)：需求與決定缺乏可追溯的紀錄，每次領導更換就重新來過。

## 小測驗

週會上，應用團隊主管說：「IP 變更我們會處理。」身為 PM，最好的回應是？

- A. 說「謝謝」，在紀錄寫下「應用團隊負責 IP 變更」
- B. 當場問：「請問由哪一位負責？預計哪一天完成？需要我們提供什麼？」然後寫成一條有人名與日期的行動項目
- C. 會後私下寄信給他，請他補上負責人與日期
- D. 不用記，主管已經承諾了

??? success "看答案與解析"
    **答案是 B。**

    - **A 錯：** 「應用團隊」不是一個人，「會處理」沒有日期。這條紀錄看起來有交代，但無法追蹤，也無法在逾期時被發現。
    - **B 對：** 在所有人面前把承諾變成「一個人、一件事、一個日期」，而且多問一句「需要我們提供什麼」，順手把相依關係找出來，見 [W-09 RAID 日誌](W-09-raid-log.md)。
    - **C 不夠好：** 比 A 好，但會後補問會讓承諾變得模糊，而且其他與會者沒有聽到確認後的版本。
    - **D 錯：** 口頭承諾最容易在幾週後變成「我以為你們會做」。見 [T-19 責任分派與 RACI](../theory/T-19-raci.md)。
