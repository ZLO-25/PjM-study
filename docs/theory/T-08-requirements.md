# T-08 需求蒐集與定義 (Requirements Elicitation & Definition)

**需求是「利害關係人需要專案交付什麼、做到什麼程度」的具體描述；蒐集需求不是記錄對方說的話，而是挖出對方真正要解決的問題。**

```text
 對方說的        →  背後的需要       →  可驗證的需求
 （解法）           （問題）            （驗收依據）
 ──────────        ──────────          ──────────────
 「我要 10G」  →   「備份太慢，     →   「夜間備份須在
                     早上還沒跑完」      06:00 前完成」

 需求的層次
 ┌─ 業務需求：組織要達成什麼
 ├─ 利害關係人需求：各群體要什麼
 ├─ 解決方案需求
 │   ├─ 功能性：系統要做什麼
 │   └─ 非功能性：效能、可用性、安全
 └─ 轉移需求：上線、訓練、移交
```

=== "入門"

    **白話解釋**

    常見的需求蒐集方法：訪談、工作坊、觀察使用者實際工作、問卷、檢視現有文件與系統、原型 (Prototype)。

    好的需求要能被驗證。判斷方法：問「上線那天，我要怎麼證明這個需求有被滿足？」如果答不出來，這個需求還不夠具體。

    **IT 例子**

    使用者說：「網路要穩。」
    追問後可能變成：「營業時間內，單一設備故障不得中斷服務」（可用性需求）、「切換時間小於 1 秒」（效能需求）、「故障時要在 5 分鐘內通知值班人員」（維運需求）。

    **最常見的誤解**

    「需求就是使用者說要什麼就給什麼。」使用者常常直接說出**解法**（我要 10G），而不是**問題**（備份太慢）。如果只照解法做，可能花了錢卻沒解決問題，因為瓶頸可能在儲存設備而不是網路。

=== "進階"

    **取捨與兩難**

    - **預測式**：盡量在開工前確認需求，適合需求穩定、變更成本高的工作（例如實體機房）。
    - **敏捷**：只先確認高階需求，細節在每一輪迭代中與使用者一起確認，適合需求不明確、可以快速試錯的工作（例如軟體介面）。
    - 非功能性需求（效能、可用性、安全）常被遺漏，但它們最難在後期補救。

    **跨主題的互動**

    - 需求要能追溯到驗收，見 [W-03 需求追溯矩陣](../practice/W-03-requirements-traceability.md) 與 [T-18 驗收標準與完成定義](T-18-acceptance-criteria.md)。
    - 利害關係人說的需求背後常有沒說出口的顧慮，見 [P-01 利害關係人的動機與恐懼](../psychology/P-01-stakeholder-motives.md)。

    **資深 PM 怎麼判斷**

    資深 PM 會為每個需求追問「如果不做，會怎樣？」。答案是「也還好」的需求，通常可以排到後面，或者根本不需要。

## 明天上班可以怎麼用

- 挑你目前專案中三個最重要的需求，檢查它們是不是「可驗證」的寫法。
- 下次使用者說「我要 X」，先問「X 是要解決什麼問題？」至少追問兩次「為什麼」。
- 檢查需求清單有沒有非功能性需求：效能、可用性、安全、可維運性。

## 小測驗

業務單位說：「我們要把所有分公司的網路頻寬都升級成兩倍。」你最好的下一步是？

- A. 立刻向廠商詢價
- B. 告訴對方預算不夠，請他們降低需求
- C. 詢問他們遇到什麼問題、在哪些分公司、什麼時段發生，並查看現有流量資料
- D. 先升級一個分公司試試看

??? success "看答案與解析"
    **答案是 C。**

    - **A 錯：** 「兩倍頻寬」是解法，不是問題。直接詢價可能花大錢卻解決不了真正的問題。
    - **B 錯：** 還沒了解問題就拒絕，會傷害合作關係，也可能錯過真正重要的需求，見 [P-06 說不與期望管理](../psychology/P-06-saying-no.md)。
    - **C 對：** 從解法回推問題，並用資料驗證，才能定義出可驗證的需求。
    - **D 錯：** 試點是好方法，但必須先知道要驗證什麼，否則試完也無法判斷成功與否。
