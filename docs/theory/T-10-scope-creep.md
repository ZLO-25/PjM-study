# T-10 範疇蔓延 (Scope Creep)

**範疇蔓延是專案範疇在沒有經過正式評估與核准的情況下，一點一點被擴大；每一次看起來都很小，累積起來卻足以拖垮時程、預算和團隊。**

```text
 原始範疇            實際範疇
 ┌──────────┐        ┌──────────┐
 │          │        │          │ + 順便加的報表
 │  核准的  │  ───►  │  核准的  │ + 「只要兩天」的功能
 │   範疇   │        │   範疇   │ + 口頭答應的整合
 │          │        │          │ + ……
 └──────────┘        └──────────┘
 時程、預算不變       時程、預算還是不變？
                       ↓
                   團隊加班、品質下降、最後延誤
```

=== "入門"

    **白話解釋**

    範疇蔓延的關鍵不是「範疇變大」，而是「**沒有經過決策就變大**」。專案範疇本來就可能改變，問題在於改變時沒有同步調整時程、成本，也沒有人正式同意這個取捨。

    常見來源：

    - 利害關係人在走廊上、會議後口頭提出的「小要求」。
    - 團隊自己覺得「順便做比較完整」的鍍金 (Gold Plating)。
    - 需求一開始沒寫清楚，模糊地帶被各自解讀。

    **IT 例子**

    網路建置專案進行中，應用團隊說：「既然你們在設定防火牆，順便把我們新系統的規則也加一下。」看起來只是幾條規則，但新系統的規則需要資安審查、測試、文件更新，最後多花了兩週，而原本的割接日期沒變。

    **最常見的誤解**

    「防止範疇蔓延 = 拒絕所有變更。」錯。拒絕所有變更會讓專案交付一個沒人要的東西。正確做法是**讓每個變更都被看見、被評估、被決定**。

=== "進階"

    **取捨與兩難**

    - **【預測式】** 用範疇基準和變更控制委員會 (Change Control Board, CCB) 管理變更。缺點是流程慢，若變更很多，CCB 會變成瓶頸。
    - **【敏捷】** 擁抱變化，但用「固定時間盒、彈性範疇」處理：新需求進待辦清單，由產品負責人 (Product Owner) 排序，加一個就要拿掉或延後另一個。範疇蔓延在敏捷中的樣子是「每個 Sprint 都塞超過團隊能做的量」。
    - **什麼時候不適用嚴格控制**：探索型專案（研究、概念驗證）本來就預期範疇會改變，嚴格控制會扼殺學習。

    **跨主題的互動**

    - 變更控制的機制見 [T-23 整合變更控制](T-23-change-control.md)。
    - PM 不好意思說「不」是範疇蔓延的主要心理原因之一，見 [P-06 說不與期望管理](../psychology/P-06-saying-no.md)。
    - 範疇基準本身寫不清楚，蔓延就無從判斷，見 [T-09 WBS 與範疇基準](T-09-wbs-scope-baseline.md)。

    **資深 PM 怎麼判斷**

    資深 PM 不會問「這個要求大不大」，而是問「**這個要求有沒有被記錄、有沒有人評估影響、有沒有對的人同意**」。小變更可以快速核准，但一定要留下紀錄，這樣半年後才說得清楚專案為什麼延誤。

## 明天上班可以怎麼用

- 準備一句話，下次有人提出「順便」的要求時用：「好，我先記下來，評估一下對時程的影響，明天回你。」
- 建立一份簡單的「變更紀錄表」，即使是口頭答應的小事也記下來，模板見 [W-16 變更請求單](../practice/W-16-change-request.md)。
- 每兩週回頭看一次：目前的工作有哪些不在原本的範疇基準裡？

## 對照案例

- [C-01 Denver 機場行李系統](../cases/C-01-denver-airport-baggage.md)：自動化行李系統的範圍在建造過程中擴大，時程卻被固定在機場開幕日。
- [C-02 HealthCare.gov](../cases/C-02-healthcare-gov.md)：在法定上線日不變的情況下，需求持續變動到開發後期。
- [C-03 FBI Virtual Case File](../cases/C-03-fbi-virtual-case-file.md)：需求在開發期間大量變動，最終系統無法交付。

## 小測驗

在 Sprint 進行到一半時，產品負責人想加入一個「很小」的新使用者故事。團隊估計需要兩天，而這個 Sprint 已經排滿。最符合敏捷原則的做法是？

- A. 直接加進來，團隊加班完成
- B. 拒絕，下一個 Sprint 再說，不需要討論
- C. 請產品負責人決定：要嘛把它放到下一個 Sprint，要嘛拿掉本 Sprint 中份量相當、尚未開始的項目來換
- D. 團隊自行決定要不要做

??? success "看答案與解析"
    **答案是 C。**

    - **A 錯：** 時間盒固定、容量固定，硬加就是範疇蔓延，會犧牲品質或讓其他項目完成不了。
    - **B 錯（不完全錯）：** 放到下一個 Sprint 是可行選項，但不討論直接拒絕，忽略了產品負責人可能有重要的理由。
    - **C 對：** 敏捷用「交換」管理範疇：容量不變，優先順序由產品負責人負責。這讓取捨變得明確，見 [T-25 敏捷價值與 Scrum](T-25-agile-scrum.md)。
    - **D 錯：** 團隊決定「怎麼做」，但「做什麼、先做什麼」是產品負責人的責任。
