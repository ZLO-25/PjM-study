# T-16 風險、議題與假設 (Risk vs. Issue vs. Assumption)

**風險是「可能發生」的事，議題是「已經發生、正在影響專案」的事，假設是「我們當作真的、但還沒證實」的事；三者要分開追蹤，因為處理方式完全不同。**

```text
 假設 Assumption      風險 Risk          議題 Issue
 「我們認為…」        「可能會…」        「已經…」
     │                    │                  │
     │ 被證明不成立        │ 真的發生          │
     └──────────►─────────┴────────►─────────┘
                                             │
                                             ▼
                                   需要決定、需要行動
                                   必要時升級上報

 處理時間點：
 假設 → 驗證        風險 → 預防與準備     議題 → 解決
```

=== "入門"

    **白話解釋**

    | | 假設 | 風險 | 議題 |
    |---|---|---|---|
    | 時態 | 現在當作真的 | 未來可能 | 現在已經發生 |
    | 問題 | 是真的嗎？ | 會發生嗎？ | 怎麼解決？ |
    | 動作 | 找證據驗證 | 規劃回應 | 指派負責人、訂期限 |

    很多專案用 **RAID 日誌** 一起追蹤：Risks（風險）、Assumptions（假設）、Issues（議題）、Dependencies（相依），見 [W-09 RAID 日誌](../practice/W-09-raid-log.md)。

    **IT 例子**

    - 假設：「新機房的電力會在 3 月 1 日前到位。」
    - 風險：「因為電力工程排程緊湊，可能延誤，導致設備無法上架。」
    - 議題：「電力工程已確定延到 3 月 15 日，設備上架必須順延。」

    **最常見的誤解**

    「把議題寫成風險，看起來比較不嚴重。」這是一種常見的自我欺騙。已經發生的事如果還寫成「可能」，就不會有人去解決它。

=== "進階"

    **取捨與兩難**

    - 假設最容易被忽略，因為它們通常寫在專案計畫的某一頁之後就被遺忘。但很多專案失敗的根源，正是某個早期假設不成立。
    - 議題太多時，PM 可能陷入「救火」，沒時間處理風險。資深 PM 會刻意保留時間給風險，因為今天沒處理的風險就是下個月的議題。

    **跨主題的互動**

    - 議題需要決策時，要清楚地向上報告，見 [W-15 升級上報信](../practice/W-15-escalation.md)。
    - 團隊不敢把議題說出來，是 [P-15 壞消息上報延遲](../psychology/P-15-mum-effect.md) 的典型。
    - 商業論證的假設不成立時，要重新評估專案價值，見 [T-04 商業論證與效益](T-04-business-case.md)。

    **資深 PM 怎麼判斷**

    資深 PM 每個月會拿出假設清單問一次：「哪一個假設現在已經可以驗證了？」驗證過的假設就從清單上移除；不成立的假設立刻轉成風險或議題。

## 明天上班可以怎麼用

- 打開你的風險表，找出其中「其實已經發生」的項目，改列為議題並指派負責人。
- 寫下你專案最重要的三個假設，並各寫一個「什麼時候可以驗證」。
- 用 [W-09 RAID 日誌](../practice/W-09-raid-log.md) 把四類項目放在同一處管理。

## 小測驗

廠商今天通知，原定下週到貨的光纖模組因為缺料，交期延後三週。這在 RAID 日誌中應該怎麼記錄？

- A. 風險：模組可能延誤
- B. 議題：模組已確定延後三週，需要評估對時程的影響並決定對策
- C. 假設：模組會準時到貨
- D. 不用記錄，等到貨再說

??? success "看答案與解析"
    **答案是 B。**

    - **A 錯：** 延誤已經被確認，不再是「可能」。寫成風險會降低處理的急迫性。
    - **B 對：** 已發生、正在影響專案，是議題。下一步是評估影響（是否在要徑上），並指派負責人尋找對策，見 [T-11 時程網路與要徑](T-11-critical-path.md)。
    - **C 錯：** 「模組會準時到貨」原本可能是一個假設，現在它已被證明不成立，應該結案並轉成議題。
    - **D 錯：** 不記錄就無法追蹤，也無法向利害關係人說明延誤原因。
