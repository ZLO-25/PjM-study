# T-09 WBS 與範疇基準 (WBS & Scope Baseline)

**工作分解結構 (Work Breakdown Structure, WBS) 是把專案的全部交付物一層層拆成可以估算、可以指派的小塊；核准後的範疇說明、WBS 和 WBS 字典合稱範疇基準，是判斷「這算不算變更」的依據。**

```text
 1.0 新機房網路建置
  ├─ 1.1 設計
  │   ├─ 1.1.1 架構設計
  │   └─ 1.1.2 IP 與 VLAN 規劃
  ├─ 1.2 採購
  │   ├─ 1.2.1 設備
  │   └─ 1.2.2 線材
  ├─ 1.3 建置
  │   ├─ 1.3.1 機櫃與佈線
  │   └─ 1.3.2 設備上架與設定
  ├─ 1.4 測試與驗收
  └─ 1.5 專案管理

 最底層 = 工作包 (Work Package)
 可以估工時、估成本、指派一個負責人
```

=== "入門"

    **白話解釋**

    WBS 的幾個原則：

    - **以交付物為主**，不是以動作為主。寫「IP 規劃文件」比寫「規劃 IP」好，因為交付物可以檢查完成與否。
    - **100% 原則**：下一層加起來必須等於上一層的全部工作，不多也不少。不在 WBS 裡的工作，就不在範疇裡。
    - **拆到可以管理就停**：常見經驗是一個工作包約 8 到 80 工時，或一個報告週期內可以完成。這只是經驗法則，不是硬規定。

    **範疇基準 = 範疇說明 + WBS + WBS 字典**

    WBS 字典是每個工作包的說明：要做什麼、完成標準、負責人、預估工時。

    **IT 例子**

    很多網路專案的 WBS 會漏掉「1.5 專案管理」和「文件與移交」。這些工作真實存在，不寫進去，工時就會被吃掉，卻沒人知道為什麼進度落後。

    **最常見的誤解**

    「WBS 就是甘特圖。」不是。WBS 只回答「要做什麼」，不回答「什麼時候做、先後順序」。先有 WBS，再排時程，見 [T-11 時程網路與要徑](T-11-critical-path.md)。

=== "進階"

    **取捨與兩難**

    - 拆得太細，管理成本暴增；拆得太粗，無法估算也無法追蹤。可以用「漸進細化 (Progressive Elaboration)」：近期的工作拆細，遠期的先保留在高層。
    - **敏捷專案**通常不用傳統 WBS，而用產品待辦清單 (Product Backlog)；但仍然可以用類似的方式把史詩 (Epic) 拆成使用者故事 (User Story)。

    **跨主題的互動**

    - 範疇基準一旦核准，任何增減都要走 [T-23 整合變更控制](T-23-change-control.md)，這是防止 [T-10 範疇蔓延](T-10-scope-creep.md) 的主要機制。
    - WBS 的每個工作包都應該能指派到一個負責人，見 [T-19 責任分派與 RACI](T-19-raci.md)。

    **資深 PM 怎麼判斷**

    資深 PM 會請團隊成員**一起**拆 WBS，而不是自己拆好再發下去。理由有兩個：成員最清楚實際要做哪些事，而且自己參與拆解的工作，承諾感會高很多。

## 明天上班可以怎麼用

- 用便利貼和團隊一起拆一次 WBS，30 分鐘就好。看看有沒有大家各自以為「別人會做」的工作。
- 檢查你的 WBS 有沒有「專案管理」「文件」「教育訓練」「移交」這幾塊。
- 練習方法見 [W-04 拆解 WBS](../practice/W-04-wbs.md)。

## 小測驗

以下哪一個是 WBS 中比較好的工作包寫法？

- A. 「處理設備」
- B. 「核心交換器設定完成並通過連通測試」
- C. 「第 3 週工作」
- D. 「小王的工作」

??? success "看答案與解析"
    **答案是 B。**

    - **A 錯：** 是動作而且模糊，無法判斷什麼時候算完成。
    - **B 對：** 以交付物和完成標準描述，可以估算、可以驗收、可以指派。
    - **C 錯：** 用時間分類是時程的概念，不是工作分解，見 [T-11 時程網路與要徑](T-11-critical-path.md)。
    - **D 錯：** 用人分類會讓工作和人綁死，人員異動時工作就消失了，責任分派應該另外做，見 [T-19 責任分派與 RACI](T-19-raci.md)。
