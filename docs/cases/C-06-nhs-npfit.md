# C-06 英國 NHS 國家資訊計畫 (NHS National Programme for IT, NPfIT)

**一句話摘要：英國政府在 2002 年啟動、目標是讓英格蘭全國醫療體系使用共同電子病歷與資訊系統的大型計畫；部分基礎建設成功交付，但核心的電子病歷系統進度遠落後，計畫於 2011 年宣布拆解。**

!!! note "閱讀說明"
    本頁區分「已知事實」與「推論詮釋」。事實部分以英國國家審計署 (National Audit Office, NAO) 與下議院公共帳目委員會 (Public Accounts Committee, PAC) 的公開報告為主。總成本的數字在不同報告與年份中有所不同，本頁採用 PAC 2013 年報告中「約 100 億英鎊」的量級描述。

```text
 計畫的組成（簡化）

 NPfIT（專案集）
  ├─ 全國基礎建設
  │   ├─ 全國網路
  │   ├─ 中央資料交換平台
  │   └─ 醫學影像系統
  │       → 普遍被認為交付較成功
  │
  └─ 地方電子病歷系統
      ├─ 依地區分給不同供應商
      └─ 進度大幅落後、部分供應商退出
          → 計畫的核心目標未達成

 2002 啟動 ─── 2011 宣布拆解 ─── 部分系統由各地自行接手
```

## 背景

=== "已知事實"

    - NPfIT 於 2002 年啟動，常被描述為當時全球最大的民用 IT 計畫之一。
    - 計畫採取中央集中採購，將英格蘭分成數個區域，各區域由一家主要供應商負責地方系統。
    - 部分組成（例如全國網路、醫學影像系統）被認為交付成功。
    - 核心的「詳細電子病歷」系統進度大幅落後，部分主要供應商在計畫期間退出。
    - NAO 與 PAC 在 2006 至 2013 年間發表多份報告，指出進度、成本、效益與臨床人員參與等方面的問題。
    - 2011 年，政府宣布拆解計畫，剩餘部分改由各地或其他機制管理。PAC 在 2013 年的報告中稱其總成本約達 100 億英鎊的量級，並批評效益遠不及預期。

=== "推論詮釋"

    - 由上而下、全國一致的做法，與各地醫療機構多樣的工作流程之間存在根本的張力。
    - 臨床人員（最終使用者）的參與不足，常被評論者列為主要原因之一。
    - 長期的合約結構使得調整方向的成本很高。

## 關鍵決策點

1. **中央集中採購**：以全國規模、少數大型合約推動。
2. **由上而下的推動方式**：使用者參與較晚、較少。
3. **在問題浮現後持續推進多年**：直到 2011 年才拆解。
4. **把成功的基礎建設與失敗的應用系統綁在同一個專案集中**：使整體評價變得複雜。

## 出了什麼事

- **已知**：電子病歷的核心目標未能達成；部分基礎建設成功並延續使用。
- **已知**：審計報告指出效益難以證明，成本遠大於已實現的效益。
- **推論**：官方說法與外部審查之間的落差，顯示報告透明度與壞消息上報是值得討論的議題。

## 反事實推演

- **分區試點**：先在一兩個地區與臨床人員共同設計並驗證，再推廣。
- **使用者共同設計**：讓醫師、護理師參與需求與驗收。
- **把專案集拆成可獨立評估的專案**：成功的基礎建設照常推進，有問題的應用系統可單獨調整或停止。
- **效益追蹤**：每個專案都有明確的效益指標與負責人。

## 可帶走的教訓

1. **規模越大，越需要分階段驗證**，一次到位的全國性推動風險極高。
2. **最終使用者的參與不是選項，而是成功條件。**
3. **專案集的價值在於協調，但也要能「分開判斷」**：好的部分繼續，壞的部分停損。
4. **報告的透明度決定了組織修正方向的速度。**

## 小測驗

本案中「全國網路」交付成功、「電子病歷」失敗。對專案集經理來說，最重要的啟示是？

- A. 專案集要麼全部成功，要麼全部失敗
- B. 專案集中的各專案應該能被獨立評估與決策；成功的部分繼續，問題部分可以單獨調整或終止
- C. 基礎建設比較簡單，所以一定會成功
- D. 不要做專案集

??? success "看答案與解析"
    **答案是 B。**

    - **A 錯：** 綁在一起評估，會讓好的部分被拖累，壞的部分被掩蓋。
    - **B 對：** 專案集的治理要能在專案層級做出不同決定，見 [T-01 專案、專案集與產品](../theory/T-01-project-program-product.md)、[T-24 治理與階段關卡](../theory/T-24-governance-stage-gates.md)。
    - **C 錯：** 基礎建設成功的原因可能是需求較明確、使用者較少需要改變工作方式，而不是「簡單」。
    - **D 錯：** 專案集本身不是問題，問題在於治理與推動方式。
