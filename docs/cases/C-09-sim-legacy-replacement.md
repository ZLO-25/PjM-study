# C-09【模擬】老舊系統汰換 (Legacy System Replacement)

**一句話摘要：一套用了十五年的內部工單系統要汰換；團隊用迭代方式開發新系統、用預測式方式規劃資料移轉與切換，過程中最大的挑戰不是技術，而是資深使用者的抗拒與舊系統中沒人記得的「隱藏功能」。**

!!! info "這是模擬案例"
    本案例為教學設計的虛構情境，不對應任何真實組織、人員或事件。

```text
 雙軌設計

 新系統開發（敏捷）
 [S1][S2][S3][S4][S5][S6]
   每兩週給使用者代表試用
          │
          ▼ 同步點：第 8 週、第 12 週
          │
 資料移轉與切換（預測式）
 [移轉設計][試移轉 1][試移轉 2][正式切換]
                                │
                          固定切換日、回退方案
```

## 背景

舊系統由一位早已離職的工程師開發，沒有完整文件。使用者約 200 人，其中十幾位資深使用者每天用它處理大量工單，非常熟練。公司決定導入新系統，預計 6 個月完成。

PM 採用混合式做法：新系統以兩週一輪的 Sprint 開發，資料移轉與切換則用詳細計畫與多次試移轉。

## 關鍵決策點

1. **選擇混合式**：軟體部分迭代，移轉與切換預測式。
2. **邀請使用者代表參與每個 Sprint 檢視**，其中刻意包含最抗拒的兩位資深使用者。
3. **第 3 個 Sprint 發現隱藏功能**：舊系統會自動把某類工單轉給特定群組，這個規則沒有寫在任何文件中。
4. **決定延後切換日兩週**，以補上隱藏功能並多做一次試移轉。

## 出了什麼事

- 最抗拒的資深使用者一開始只挑毛病。但在第 3 個 Sprint，他指出了「自動轉單」這個隱藏功能，讓團隊避免了一次上線後的嚴重問題。之後他成為新系統最重要的推廣者。
- 第一次試移轉發現約 5% 的舊資料格式不一致，需要清理規則。
- 切換日延後兩週，PM 提前向發起人說明原因與影響，發起人同意。
- 正式切換順利，上線後第一個月的使用者問題大多是操作習慣，而不是功能缺失。

## 反事實推演

- 如果用純預測式、一次寫完規格再開發：隱藏功能很可能要到上線後才被發現。
- 如果沒有邀請抗拒者參與：他可能在上線後才指出問題，而且會成為反對的聲音。

## 可帶走的教訓

1. **舊系統的行為就是需求**，沒寫在文件裡不代表不存在。
2. **最抗拒的人，常常最了解系統的細節**；讓他參與是風險管理。
3. **資料移轉一定要試移轉**，而且不只一次。
4. **延期要提早說，並說明換到了什麼。**

## 小測驗

PM 刻意邀請最抗拒的資深使用者參加 Sprint 檢視。這個做法主要對應哪個概念？

- A. 讓他知道反對無效
- B. 把抗拒者轉為參與者，處理他對失去專業與控制的顧慮，同時取得他對舊系統的深入知識
- C. 增加會議人數
- D. 讓他負責所有測試

??? success "看答案與解析"
    **答案是 B。**

    - **A 錯：** 參與的目的不是壓制，而是處理顧慮。
    - **B 對：** 這同時處理了變革抗拒（[P-02](../psychology/P-02-resistance-to-change.md)）與需求蒐集（[T-08](../theory/T-08-requirements.md)）。
    - **C 錯：** 人數本身不是目的。
    - **D 錯：** 讓單一使用者負責所有測試不合理，也可能讓他覺得被丟了額外工作。
