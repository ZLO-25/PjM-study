# C-05 Berlin Brandenburg 機場 (Berlin Brandenburg Airport, BER)

**一句話摘要：德國首都的新機場在原定開幕前幾週宣布延期，主因之一是消防排煙系統等技術問題；之後又歷經多次延期，最終在原定日期的約九年後才開幕，成本遠超原預算。**

!!! note "閱讀說明"
    本頁區分「已知事實」與「推論詮釋」。BER 的總成本在不同報導中計算方式不同（是否含利息、擴建、營運損失等），本頁不引用單一精確金額，只描述為「數十億歐元、遠超原始預算」。

```text
 時間線（概略）

 2006  動工
   │
 2011  原定開幕 ── 延期
   │
 2012  新開幕日前數週宣布延期
   │   （消防與排煙系統等問題）
   │
 2012–2019  多次重新規劃、多次延期
   │        負責單位與人事多次更換
   │
 2020  10 月正式開幕（較原定晚約九年）

 業主：柏林市、布蘭登堡邦、德國聯邦政府
```

## 背景

=== "已知事實"

    - BER 由柏林市、布蘭登堡邦與德國聯邦政府共同持有的公司負責興建。
    - 工程於 2006 年動工，原定 2011 年開幕，後改為 2012 年 6 月。
    - 2012 年 5 月，在開幕前數週宣布延期，主要原因之一是消防與排煙系統無法通過驗收。
    - 之後陸續發現大量施工與設計缺陷，開幕日期多次延後，管理層也多次更換。
    - 柏林市議會成立了調查委員會調查此案。
    - 機場於 2020 年 10 月 31 日開幕，比最初計畫晚了約九年。

=== "推論詮釋"

    - 多方共同持有，使得「誰是真正的當責者」不明確，決策與監督的責任分散。這是許多評論者的共同觀點。
    - 建造期間的設計變更（例如擴大航廈規模、增加商業空間）被認為加重了技術複雜度，但各項變更的影響程度在公開資料中不易精確量化。

## 關鍵決策點

1. **治理結構**：三個政府層級共同擁有，監事會成員多為政治人物。
2. **建造中的設計變更**：航廈規劃與功能在建造期間調整。
3. **對外公布開幕日**：在系統整合尚未驗證時，就確定並公開日期。
4. **開幕前數週才宣布延期**：問題直到最後的驗收階段才被正式確認。

## 出了什麼事

- **已知**：多次延期，成本大幅增加，舊機場必須持續營運多年。
- **已知**：開幕時已有部分設施需要擴建或調整。
- **推論**：「直到驗收時才發現無法通過」顯示整合與品質的問題沒有在早期被看見或被上報。

## 反事實推演

- **單一明確的當責者**：由具備專業能力的單一負責人主導，而不是分散在多個政治機構。
- **整合驗收提前**：消防、排煙這類跨系統的功能，在建造中期就進行分段驗證，而不是等到開幕前。
- **開幕日以驗收條件決定**：先定義「開幕條件」，條件達成後才公布日期。

## 可帶走的教訓

1. **當責者不明確的專案，壞消息找不到出口。**
2. **跨系統的整合功能（例如消防）要盡早驗證**，它們最難在後期補救。
3. **公開日期之前，先確認關鍵驗收條件**。
4. **IT 基礎架構也適用**：機房的電力、空調、消防與網路的整合測試，同樣需要提早。

## 小測驗

本案對 IT 基礎架構專案（例如新機房建置）最直接的啟示是？

- A. 不要蓋新機房
- B. 跨系統的整合驗證（電力、空調、消防、網路）要在建置中期分段進行，並以驗收條件決定啟用日
- C. 盡量把啟用日訂早一點，給團隊壓力
- D. 多找幾個單位共同負責，分散風險

??? success "看答案與解析"
    **答案是 B。**

    - **A 錯：** 案例的教訓是怎麼做好，不是不做。
    - **B 對：** 最難的問題往往在系統之間的介面，提早分段驗證能讓問題在可補救的時候浮現，見 [T-18 驗收標準與完成定義](../theory/T-18-acceptance-criteria.md)。
    - **C 錯：** 用不實際的日期製造壓力，正是規劃謬誤與錨定效應的來源。
    - **D 錯：** 共同負責常變成無人負責，見 [T-19 責任分派與 RACI](../theory/T-19-raci.md)。
