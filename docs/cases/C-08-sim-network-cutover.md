# C-08【模擬】核心網路割接 (Core Network Cutover)

**一句話摘要：一次 4 小時窗口的核心交換器割接，在第 2 小時遇到非預期的路由問題；團隊在「再試一下」與「依計畫回退」之間掙扎，最後依事先定義的決策點回退，兩週後重新割接成功。**

!!! info "這是模擬案例"
    本案例為教學設計的虛構情境，不對應任何真實組織、人員或事件。

```text
 割接當晚

 22:00 ┬─ 開始，全員上線
 22:15 ├─ 備份完成
 22:30 ├─ 舊設備上行介面關閉
 23:10 ├─ 新設備路由建立 ── 部分網段不通
 23:40 ├─ 排查中，工程師：「再 20 分鐘應該可以」
 00:00 ├─ ◆ 回退決策點：關鍵驗證未通過
       │    指揮官宣布回退
 00:50 ├─ 回退完成，驗證服務正常
 01:30 ┴─ 結束

 兩週後：修正設定、完整演練，重新割接成功
```

## 背景

公司要把老舊的核心交換器換成新型號。割接窗口是週六 22:00 到週日 02:00。割接計畫包含步驟表、回退方案，以及一個寫明的回退決策點：「00:00 時若關鍵驗證未全部通過，即回退」。回退演練實測需要 50 分鐘。

## 關鍵決策點

1. **割接前**：演練在實驗室完成，但實驗室的路由表規模比生產環境小得多。
2. **23:40**：資深工程師判斷「再 20 分鐘應該可以修好」，要求延後決策點。
3. **00:00**：割接指揮官（由 PM 指定的網路主管）依計畫宣布回退。
4. **事後**：團隊舉行不究責的復盤。

## 出了什麼事

回退順利，週日早上服務正常。復盤發現，新設備在大量路由條目下有一個預設參數限制，實驗室因規模小而沒有觸發。

當晚堅持「再試一下」的資深工程師，在復盤中說：「如果當時多試 20 分鐘，可能真的會修好，但也可能不會，那時就來不及回退了。」團隊同意把「演練環境的規模要接近生產環境」列為新的檢查項目。

兩週後，在修正參數並用較大規模的路由表演練後，重新割接在 2 小時內完成。

## 反事實推演

- 如果決策點被延後 20 分鐘，而問題沒修好：回退要到 00:20 才開始、01:10 完成，離窗口結束只剩 50 分鐘。如果到時又有人說「再 20 分鐘」，或回退本身遇到狀況，服務就可能在窗口結束後仍未恢復。決策點一旦可以被延後一次，就很容易被延後第二次。
- 如果演練時使用接近生產規模的路由表，問題可能在割接前就被發現。

## 可帶走的教訓

1. **決策點要事先寫好，而且要有一個人有權執行。**
2. **回退不是失敗**，是計畫的一部分。
3. **演練環境的規模與設定要接近生產環境**，否則演練會給人錯誤的信心。
4. **復盤時，把「當時的判斷」當作資訊，而不是錯誤。**

## 小測驗

23:40 時，資深工程師要求把決策點延後 20 分鐘。如果你是割接指揮官，最好的回應是？

- A. 同意，他最資深
- B. 拒絕並立即回退
- C. 確認他目前的排查方向，但說明 00:00 的決策點不會延後；請他在 00:00 前盡力排查，到時若驗證仍未通過，就依計畫回退
- D. 打電話問處長

??? success "看答案與解析"
    **答案是 C。**

    - **A 錯：** 決策點是為了在壓力下保護大家而事先設計的，臨時延後會讓它失去作用。
    - **B 錯：** 還沒到決策點，提前回退會浪費剩下的排查時間。
    - **C 對：** 尊重工程師的專業與努力，同時守住事先約定的規則，見 [W-11 割接計畫與回退方案](../practice/W-11-cutover-rollback.md)。
    - **D 錯：** 割接中的決策權應該在現場指揮官手上；如果每個決定都要往上問，會浪費寶貴的時間。
