# C-02 HealthCare.gov 上線 (HealthCare.gov Launch)

**一句話摘要：美國聯邦健康保險交易平台在法定日期上線，但因整合、測試與管理問題，上線初期大部分使用者無法完成註冊，之後經過密集修復才恢復運作。**

!!! note "閱讀說明"
    本頁區分「已知事實」與「推論詮釋」。事實部分以美國審計總署 (GAO) 與衛生及公共服務部監察長辦公室 (HHS OIG) 的公開報告為主，細節以原始報告為準。

```text
 參與方與整合關係（簡化）

 聯邦主管機關（CMS）── 擔任系統整合者
   │
   ├─ 承包商 A：網站與交易平台
   ├─ 承包商 B：資料樞紐（連接各機關資料）
   ├─ 其他多家承包商
   │
   └─ 外部系統：國稅、社安、國土安全等機關

 整合責任集中在一個缺乏大型整合經驗的單位
```

## 背景

=== "已知事實"

    - 平台是《平價醫療法》(Affordable Care Act) 的核心系統，讓民眾比較並購買健康保險。
    - 平台於 2013 年 10 月 1 日上線，這個日期與法律的時程有關，政治上難以更改。
    - 系統由多家承包商分別開發，由聯邦主管機關 CMS 負責整合。
    - GAO 與 HHS OIG 的報告指出，主管機關在規劃、合約管理、需求管理與監督上有多項缺失。
    - 上線初期，網站發生嚴重的效能與功能問題，大多數使用者無法完成流程。
    - 之後政府組織了密集的修復行動，網站在數個月內大幅改善。主要承包商在 2014 年初被更換。

=== "推論詮釋"

    - 「固定日期 + 需求晚定 + 多方整合 + 測試不足」是典型的高風險組合。
    - 監察長報告將問題的根源歸納為領導與管理層面，而不只是技術；本手冊認為這反映了利害關係人眾多、決策權分散的困難。

## 關鍵決策點

1. **由主管機關自己擔任整合者**，而不是交給有經驗的整合商。
2. **在需求尚未穩定時開始開發**，且需求變更持續到開發後期。
3. **端對端整合測試時間被壓縮**，上線前未能在真實規模下驗證。
4. **維持原上線日**，而不是縮小上線範圍或分階段開放。

## 出了什麼事

- **已知**：上線後網站大量錯誤、回應緩慢，註冊人數遠低於預期。
- **已知**：密集修復期間，團隊改以較小、較頻繁的方式修正與部署（依公開報導）。
- **推論**：上線前的風險訊號（測試不足、整合未完成）在報告中有被提及，但這些訊號未能改變「準時上線」的決定。

## 反事實推演

- **縮小首日範圍**：例如先開放瀏覽與比較方案，註冊功能分批開放；或先在部分州開放。
- **獨立的整合者**：由有經驗的單位負責整合與端對端測試，並給予足夠的權限。
- **上線關卡**：事先定義上線條件（例如在預期負載下完成端對端流程），未達條件時提出降級上線的選項，見 [T-24 治理與階段關卡](../theory/T-24-governance-stage-gates.md)。

## 可帶走的教訓

1. **日期固定時，範疇必須有彈性**；兩者都固定，犧牲的就是品質。
2. **整合是一項獨立的工作**，需要明確的當責者與足夠的時間。
3. **在真實規模下測試**，特別是面對大量使用者的系統。
4. **修復階段的做法（小步快跑）值得學習**：當不確定性很高時，頻繁交付與快速回饋是降低風險的方法。

## 小測驗

如果你是當時的 PM，上線前兩週發現端對端測試只完成一小部分，而上線日不能改。最負責任的做法是？

- A. 照原計畫全面上線，上線後再修
- B. 向決策者提出降級上線選項（例如只開放部分功能或部分地區），清楚說明全面上線的風險，由決策者選擇
- C. 不說，讓團隊加班
- D. 宣布延期

??? success "看答案與解析"
    **答案是 B。**

    - **A 錯：** 把已知風險直接交給使用者承擔，而且決策者沒有機會看見取捨。
    - **B 對：** 日期固定時，用範疇換取品質；並確保決策者在完整資訊下做選擇，見 [T-24 治理與階段關卡](../theory/T-24-governance-stage-gates.md)。
    - **C 錯：** 加班無法在兩週內補足大量整合測試，也隱藏了風險，見 [P-15 壞消息上報延遲](../psychology/P-15-mum-effect.md)。
    - **D 錯：** 延期的決定權不在 PM，而且題目設定日期不能改。
