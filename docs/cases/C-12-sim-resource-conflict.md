# C-12【模擬】跨部門資源爭奪 (Cross-Team Resource Conflict)

**一句話摘要：兩個專案在同一個月都需要同一位資深網路工程師，兩位 PM 各自向他施壓，他夾在中間開始延誤兩邊的工作；最後由兩位 PM 和他的職能經理一起，用要徑與業務影響來排定優先順序。**

!!! info "這是模擬案例"
    本案例為教學設計的虛構情境，不對應任何真實組織、人員或事件。

```text
 衝突的結構

      專案 X PM            專案 Y PM
          │                    │
          └──► 資深工程師 ◄────┘
                   │
                   ▼
              職能經理（網路部）
              擁有他的時間分配權

 第 3 週的狀態
 專案 X：他承諾的設定延誤 4 天
 專案 Y：他承諾的審查延誤 3 天
 他本人：每天加班到深夜

 解法：三方會議
 ┌─ 把兩邊需求攤在同一張時間表上
 ├─ 用「要徑 + 業務影響」排序
 └─ 職能經理決定分配，並安排一位支援人員
```

## 背景

專案 X 是資料中心網路擴充，專案 Y 是新的網路監控平台。兩個專案都需要同一位資深網路工程師，他是部門裡唯一熟悉現有架構的人。兩位 PM 在規劃時都假設他可以投入 50%，卻沒有人跟職能經理確認，他同時還有日常維運工作。

## 關鍵決策點

1. **規劃時**：兩位 PM 各自假設可以使用他 50% 的時間，沒有和職能經理對齊。
2. **第 2 週**：兩邊都開始私下催他，他兩邊都答應。
3. **第 3 週**：兩邊都延誤。專案 X 的 PM 考慮向處長投訴。
4. **選擇**：專案 X 的 PM 改為邀請專案 Y 的 PM 與職能經理開三方會議。

## 出了什麼事

三方會議中：

- 兩位 PM 把各自需要他的工作、時間、是否在要徑上、延誤的業務影響，攤在同一張表上。
- 發現專案 X 的工作在要徑上，延誤會影響一個已對外承諾的日期；專案 Y 的審查不在要徑上，有兩週浮時。
- 職能經理決定：接下來兩週優先專案 X，專案 Y 的審查延後並由另一位工程師先做初審；同時安排一位資淺工程師跟著他學習，作為長期的交叉訓練。
- 兩位 PM 約定：未來對這位工程師的需求，先透過職能經理排程，不再私下直接要求。

兩個專案都延誤了幾天，但都在可接受範圍內。這位工程師在復盤中說，最大的壓力不是工作量，而是「兩邊都覺得我在偏袒對方」。

- [T-20 矩陣式組織](../theory/T-20-matrix-organization.md)：職能經理擁有時間分配權。
- [T-11 時程網路與要徑](../theory/T-11-critical-path.md)：用要徑與浮時決定優先順序。
- [T-27 看板與流動](../theory/T-27-kanban-flow.md)：多工讓每件事都變慢。

## 對應心理 (P)

- [P-04 原則式談判與 BATNA](../psychology/P-04-principled-negotiation.md)：用客觀標準（要徑、業務影響）代替立場。
- [P-13 衝突處理模式](../psychology/P-13-conflict-modes.md)：從競爭轉向合作。
- [P-09 PM 的壓力與倦怠](../psychology/P-09-pm-stress.md)：夾在中間的成員的壓力。
- [P-03 沒有職權的影響力](../psychology/P-03-influence-without-authority.md)：兩位 PM 都沒有權力直接分配他的時間。
- [P-16 新手 PM 的冒牌者感與討好傾向](../psychology/P-16-rookie-pm-traps.md)：工程師「兩邊都答應」是典型的討好反應，代價由兩個專案一起付。

## 反事實推演

- 如果專案 X 的 PM 直接向處長投訴：可能換來短期的優先，但專案 Y 的 PM 會覺得被越級，職能經理也會覺得被跳過；這位工程師的壓力不會減輕。
- 如果規劃時兩位 PM 就和職能經理確認他的可用時間：衝突在規劃階段就會被發現，可以提早安排支援人力。

## 可帶走的教訓

1. **不要在沒和職能經理確認的情況下，假設一個人的可用時間。**
2. **資源衝突要用客觀標準解決**，例如要徑、業務影響。
3. **不要讓成員自己在兩個 PM 之間選邊**，這是 PM 和職能經理的責任。
4. **單點故障人物要有交叉訓練計畫**。

## 小測驗

第 3 週，專案 X 的 PM 考慮直接向處長投訴。為什麼「三方會議」是比較好的選擇？

- A. 因為處長很忙
- B. 因為三方會議讓雙方的需求在同一個基準上比較，由擁有分配權的職能經理依客觀標準決定，同時保護了工程師與兩位 PM 之間的關係
- C. 因為投訴一定會輸
- D. 因為三方會議比較快

??? success "看答案與解析"
    **答案是 B。**

    - **A 錯：** 處長忙不忙不是重點，如果三方會議無法解決，升級仍然是合理的選項，見 [W-15 升級上報信](../practice/W-15-escalation.md)。
    - **B 對：** 合作模式（[P-13](../psychology/P-13-conflict-modes.md)）+ 客觀標準（[P-04](../psychology/P-04-principled-negotiation.md)）+ 尊重矩陣組織的權責（[T-20](../theory/T-20-matrix-organization.md)）。
    - **C 錯：** 投訴不一定會輸，但即使「贏」了，也可能損害長期的合作關係。
    - **D 錯：** 不一定比較快，但通常比較持久。
